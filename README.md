# Агент рабочей станции восстановления данных

Ставится на машину лаборатории, где лежат образы и восстановленные файлы. Отдаёт
нашему бэкенду дерево папок и сами файлы, чтобы клиент видел свои данные в
веб-просмотрщике. Ничего не пишет — только чтение.

Нужен Python 3.10+ (на 3.8–3.9 не запустится: аннотации `Path | None`). Внешних библиотек нет.

## Установка

**1. Сертификат** (самоподписанный, на 10 лет). В Git Bash:

```bash
cd tools/lab_agent
openssl req -x509 -newkey rsa:2048 -nodes -days 3650 \
  -keyout station.key -out station.crt -subj "/CN=lab-station"
```

**2. Токен** — длинная случайная строка:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

**3. Конфиг** `agent.ini` рядом со скриптом:

```ini
[agent]
name = LAB-1
port = 47821
token = <строка из шага 2>
certfile = station.crt
keyfile = station.key
; Что агент имеет право отдавать. Через ';'. Всё вне этих папок недоступно.
data_roots = H:\;J:\
; IP нашего сервера. Через запятую. Пустое значение = принимать всех — не надо так.
allow_ips = 203.0.113.10
; Журнал: новый файл каждую полночь, хранится logfile_days суток (по умолчанию 14).
logfile = C:\lab\logs\agent.log
; logfile_days = 14
; Необязательно. Папка заданий (ручки /jobs…). Нет строки — задания выключены,
; агент только читает, как раньше. Включать — только с «да» владельца.
; jobs_dir = C:\lab\jobs
```

Порт берите нестандартный, пятизначный — сканеры ходят по типовым.

**4. Проброс порта** на роутере: внешний `47821` → внутренний IP станции, тот же
порт. Только TCP.

**5. Запуск:**

```bash
python agent.py --config agent.ini
```

Чтобы поднимался сам после перезагрузки — задача «Планировщика заданий» Windows:
триггер «При запуске компьютера», «Выполнять вне зависимости от регистрации
пользователя», перезапуск при сбое каждую минуту, без ограничения времени;
программа — `pythonw.exe` (без чёрного окна), аргументы `agent.py --config agent.ini`,
рабочая папка — папка агента. Под `pythonw` консоли нет — всё, что агент пишет,
только в `logfile`. Проверка: перезагрузить ПК и, не входя в систему, нажать «Пинг»
на `/lab-stations`.

**6. Регистрация в админке.** `/lab-stations` → «Добавить»: имя, host (белый IP),
порт, токен, корни. Кнопка «Получить отпечаток» заберёт сертификат и покажет его
sha256 — сверьте с локальным выводом и сохраните:

```bash
openssl x509 -in station.crt -noout -fingerprint -sha256
```

Дальше бэкенд доверяет ровно этому сертификату: подменный даст другой отпечаток,
и соединение не состоится.

## Защита

Три слоя, каждый работает сам по себе:

1. **Токен** — без заголовка `Authorization: Bearer …` любой запрос получает 401.
   Сравнение через `hmac.compare_digest`, подобрать по времени ответа нельзя.
2. **TLS с пиннингом** — сертификат самоподписанный, но бэкенд сверяет его
   отпечаток с сохранённым. Это строже обычного HTTPS: доверяем одному
   конкретному сертификату, а не любому, что выдал какой-нибудь CA.
3. **Allowlist IP** — агент отвечает только с адреса нашего сервера. Остальным
   403 ещё до проверки токена.

Наружу отдаётся только то, что внутри `data_roots`. Каждый путь приводится к
абсолютному с раскрытием симлинков и проверяется на принадлежность корню, так что
`..\..\Windows\System32` и абсолютные пути мимо корней не работают.

Чего агент не умеет намеренно: удалять и запускать что-либо. Без `jobs_dir` он и не
пишет: максимум, что даёт компрометация токена, — чтение файлов внутри корней.
С `jobs_dir` добавляется запись — только в `jobs_dir/<job_id>/` и только своих файлов
(`job.json`, `answers.jsonl`, `notes.jsonl`, `selection.roa`, `cancel`). Задания
исполняет отдельный процесс станции, агент его не запускает.

## Endpoints

Все требуют токен. Чтение (GET):

| Путь | Параметры | Ответ |
|---|---|---|
| `/health` | — | `{ok, name, version, commit, roots: [{path, exists}], jobs}` — `commit` из файла `REVISION` (пишет обновлятор) |
| `/station` | `lines=50` (до 500) | `{agent_version, now, runner, volumes: [{letter, type, label, fs, total, free}], logs: [{name, size, mtime, tail}]}` — пульс исполнителя из `jobs_dir/_runner.json` (мёртв, если `at` старше трёх `poll_seconds`), тома, хвосты `*.log` из папки `logfile` |
| `/order-dir` | `num=45685` | `{found, path}` — свежая папка заказа внутри корней |
| `/tree` | `path=H:\45685` | `{base, files: [{path, rel, size, mtime}], count, bytes, truncated}` |
| `/file` | `path=H:\45685\1.mp4` | сам файл, потоком по 1 МБ |
| `/screenshot` | — или `name=20261118-034412.png` | PNG: без `name` — свежий кадр помощника (`X-Screen-Age` — сколько секунд кадру; кадра нет или старше `screen_max_age_sec` — 409 с причиной), с `name` — кадр из ленты |
| `/screenshots` | `since=<unix-время>` | `{enabled, interval_sec, latest: {ok, age_sec | error}, last_error, items: [{name, at, size}]}` — лента, свежие первыми |
| `/disks` | `refresh=1` — пересобрать | индекс дисков (1.4): `{scanned_at, scanning, volumes, folders: [{path, name, volume, depth, order_nums, is_data, info: {model, fw, serial, port, destin, text}, images: [{kind, files, bytes, where}], subdirs}], errors}` |
| `/delivery/copies[/<id>]` | — | выгрузки на шару: `{state: queued…copying…verifying…done|failed|interrupted, files_total, bytes_total, files_done, bytes_done, skipped, verify: {src_files, src_bytes, dst_files, dst_bytes, ok, mismatch}}` |

Запись: `POST /jobs…` (задания, см. ниже) и `POST /delivery/copy {src}` — копия папки из индекса в
`delivery_root\<имя папки>` (1.4).

## Индекс дисков и выдача данных (с версии 1.4, 19.11.2026)

Задача 2480, ТЗ `TASK_data_delivery_2026-07-31.md` §0. Агент сам, в фоне, обходит все готовые локальные тома
(кроме системного) на глубину 1–2 и находит папки заказов: номер в имени (`46154_data`), паспорт задачи PC-3000
(`task.info` — модель, прошивка, серийник; cp1251), образы (куски `img<LBA>.bin` + `Head.map`, `*.deff`,
файл-образ). Чей это заказ, решает бэк — сличает с RO по номеру, серийнику, модели, названию клиента.

Выгрузка — копия папки из индекса на шару `delivery_root` под тем же именем, со сверкой числа файлов и байт.
Источник не трогается, ничего не удаляется; уже лежащий файл того же размера и времени не копируется заново.
Агент работает задачей планировщика S4U («без входа»): диск `Z:`, подключённый у пользователя, ему не виден,
и сетевых учётных данных у такого входа нет — в `delivery_root` пишется UNC-путь, учётка шары —
`delivery_user` / `delivery_password` (агент делает `net use` сам). Может ли агент писать в шару, видно сразу:
`GET /station` → `delivery: {ok, error, root, at}` (проверка пишет один свой файл `_lab_agent_write_check.txt`
в корень шары, раз в 5 минут, в фоне). Индекс только листает каталоги и читает `task.info` с
`FILE_SHARE_READ|WRITE|DELETE` — идущему снятию в PC-3000 DE не мешает; образы не открывает никогда.

```ini
index = on                       ; off — не строить индекс (GET /disks → 404)
index_skip = C                   ; тома, которые не обходить (по умолчанию — системный)
index_extra =                    ; доп. папки задач через «;». Bin каждой установки PC-3000 (Express, Portable)
                                 ; находится сам: реестр Uninstall (64 и 32 бит) → InstallLocation\Bin, плюс
                                 ; <Program Files | Program Files (x86)>\ACE Lab\*\Bin. Там задачи «напрямую с
                                 ; пациентом», без образа; у каждой задачи в индексе — product (какой PC-3000)
index_interval_min = 15          ; как часто пересобирать
delivery_root = \\kompstation\web   ; пусто — выгрузка выключена
delivery_user =                  ; учётка шары: агент — задача S4U («без входа»), сетевых учёток у неё нет
delivery_password =              ; только локально, в agent.ini; агент делает net use сам
delivery_fresh_min = 10          ; в папке менялись файлы позже — не копировать: выгрузку ещё пишут
state_dir =                      ; где лежат datapool_index.json и delivery_copies.json (пусто — рядом с agent.py)
```

## Снимки экрана (с версии 1.3, 18.11.2026)

Чтобы в кабинете было видно, что происходит на станции, не подключаясь к ней. Кабинет показывает кадр по
кнопке и ленту за сутки; сами снимки **хранятся только здесь** и уходят наружу только по запросу кабинета
(на экране — данные клиентов).

**Кто снимает.** Агент работает задачей «вне входа» (S4U, сессия 0) — он доступен и до входа в Windows, но
экрана из сессии 0 не видно. Поэтому снимает **помощник `screen_helper.py` в сессии пользователя**: раз в
`screen_latest_sec` пишет `screens/latest.png`, раз в `screen_interval_sec` — кадр в ленту (только если экран
изменился). Агент только отдаёт файлы. Никто не вошёл в Windows — снимков нет, и агент так и отвечает.

Помощник ставится один раз — задачей «при входе пользователя», интерактивно, тем же пользователем, что агент:

```bat
schtasks /Create /TN "lab_agent screens" /SC ONLOGON /RU Lab2 /IT /TR "\"C:\...\pythonw.exe\" \"C:\...\lab_agent\screen_helper.py\" --config \"C:\...\lab_agent\agent.ini\""
```

В `agent.ini` (всё необязательно):

```ini
screen_latest_sec = 30      ; свежий кадр раз в 30 с
screen_interval_sec = 300   ; лента раз в 5 минут, только если экран изменился; 0 — снимки выключены
screen_keep_hours = 24      ; сколько хранить ленту
screen_max_mb = 500         ; потолок места под ленту
screen_max_width = 1600     ; ширина снимка (все мониторы, уменьшенные)
screen_max_age_sec = 120    ; старше — агент говорит «помощник остановлен», а не отдаёт старый кадр
screens_dir =               ; пусто — папка screens рядом с agent.py
```

## Самообновление (с версии 1.3)

Код агента лежит в открытом репозитории **github.com/SheferVS/lab-agent** (только код; `agent.ini`,
сертификат, ключ, снимки, журналы — только на станции, в репозиторий не попадают). `updater.py` раз в 5 минут
спрашивает GitHub, какой коммит в ветке, и если он новый — скачивает архив этого коммита, берёт только
`agent.py, screen.py, screen_helper.py, updater.py, datapool.py` (новый файл обновлятор прежней версии не
знает — его докладывает второй проход уже нового обновлятора; больше ничего в папке не трогает — рядом могут жить
`runner.py` и прочее станционное), проверяет автора коммита и что код компилируется, сохраняет
текущие файлы в `releases/prev`, ставит новые, пишет `REVISION`, перезапускает задачи агента и помощника и
спрашивает `/health`. Агент не поднялся или поднялся не тем коммитом — откат на прежние файлы, коммит
записывается в плохие и больше не берётся. Состояние — `updater_state.json`, журнал — `updater.log`.

В `agent.ini`:

```ini
[update]
repo = SheferVS/lab-agent
branch = main
agent_task = lab_agent LAB-VLAD       ; имя задачи планировщика агента
helper_task = lab_agent screens       ; имя задачи помощника снимков (если поставлен)
auto = true                           ; false — только сообщать о новой версии (updater_state.json), ставить руками
allowed_authors = SheferVS            ; коммит от кого-то ещё (или от неизвестного GitHub автора) не ставится
```

Ставится один раз — задачей тем же пользователем, что агент (иначе не сможет перезапустить его задачу):

```bat
schtasks /Create /TN "lab_agent updater" /SC MINUTE /MO 5 /RU Lab2 /TR "\"C:\...\python.exe\" \"C:\...\lab_agent\updater.py\" --config \"C:\...\lab_agent\agent.ini\""
```

**Доверие.** Станция выполняет любой код, попавший в `main` этого репозитория. Писать в `main` может только
владелец: защита ветки и двухфакторный вход на GitHub. Выкладывает код в репозиторий
`scripts/publish_lab_agent.py` из нашего `tools/lab_agent` — источник правды у нас, репозиторий — витрина.

Задания — только при `jobs_dir` (иначе 404). Контракт и смысл — ТЗ
`SaaS-Ai-SC/docs/TASK/active/TZ_lab_station_logical_recovery_2026-11-17.md` §5, §5а.

| Метод, путь | Тело / параметры | Что делает |
|---|---|---|
| `POST /jobs` | JSON `{job_id, order_ref, …}` | кладёт `job.json`; повтор `job_id` — no-op (`existed: true`) |
| `GET /jobs/<id>` | `since=<seq>` | `{state, events: [seq > since], more}` из `state.json` и `events.jsonl` исполнителя |
| `GET /jobs` | — | `{jobs: [{job_id, order_ref, state, last_seq, updated_at}], runner}` — только папки с `job.json` |
| `GET /jobs/<id>/files` | — | опись папки задания: `{files: [{name, size, mtime}]}`, `name` через `/`, без `*.tmp` |
| `GET /jobs/<id>/file` | `name=<файл в папке задания>`, `offset=<байт>` | файл с `offset` (докачка растущей переписки и журнала), полный размер — `X-File-Size`; `offset` больше размера — 416 (файл перезаписан, качать с нуля); вне папки задания — 400 |
| `POST /jobs/<id>/answer` | `{question_id, text, from}` | строка в `answers.jsonl`, дубль — no-op |
| `POST /jobs/<id>/note` | `{note_id, text, from, at}` | строка в `notes.jsonl` — сообщение сотрудника сессии, дубль — no-op |
| `POST /jobs/<id>/selection` | `.roa` байтами | атомарно `selection.roa` |
| `POST /jobs/<id>/cancel` | `{reason, from}` | файл `cancel`, `state` → `cancel_requested` |

## Проверка после установки

```bash
# со станции — должен вернуть JSON
curl -k https://127.0.0.1:47821/health -H "Authorization: Bearer <токен>"

# с нашего сервера — то же самое по белому IP
curl -k https://<белый-ip>:47821/health -H "Authorization: Bearer <токен>"

# без токена — должен вернуть 401
curl -k https://<белый-ip>:47821/health
```

Если второй запрос не проходит, а первый проходит — дело в пробросе порта или
файрволе Windows (нужно разрешить входящие на порт агента).
